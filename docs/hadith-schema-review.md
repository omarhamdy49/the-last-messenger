# Hadith database schema review

## 1. Verdict

The schema is simultaneously over-engineered and under-engineered, not right-sized. It carries unused localization, review, provenance, application, and fiqh structures, while core contracts—Sunnah import, grading, theme hierarchy, chapter localization, Quran links, and isnad ordering—are either contradictory or unenforced. The populated core (collections, books, chapters, hadith text, isnad, themes, commentaries, and sources) is worth retaining, but the clean rebuild should collapse competing representations before any data is re-imported. The purge makes the recommended table drops, column merges, and key changes unusually cheap; they would be materially riskier after repopulation.

## 4. Under-engineering — ADD or CONSTRAIN

1. **Gate the rebuild on one MySQL-native import contract.** A one-collection smoke import must assert collection→book→chapter→hadith counts, required Arabic text, source identity, idempotent second run, FK integrity, and preservation of every source grade/grader. SQLite cannot validate MySQL column drift or FULLTEXT behavior demonstrated above (`app/Domain/Hadith/Services/HadithSyncService.php:264-274`, `docs/hadith-schema.json:870-879`).

2. **Use relational keys for the actual hierarchy.** Require `books.collection_id`, `chapters.book_id`, and `hadiths.chapter_id`; create a deliberate “unsectioned” chapter rather than nullable hierarchy. Add unique `(collection_id, book_number)`, unique `(book_id, chapter_number)`, and index `(chapter_id, hadith_number)`. Current repositories query these pairs but the live books/chapters keys are non-unique (`app/Domain/Hadith/Repositories/BookRepository.php:163-167`, `app/Domain/Hadith/Repositories/ChapterRepository.php:63-67`, `docs/hadith-schema.json:73-78`, `docs/hadith-schema.json:112-116`).

3. **Make source identity idempotent and non-null.** `hadith_sources` needs unique `(source_system, external_id)` when the external identifier is globally stable, otherwise `(source_system, collection_code, external_id)`. The current unique key contains nullable file/URL parts, so MySQL can admit multiple “duplicates” with NULLs (`docs/hadith-schema.json:624-647`, `app/Domain/Hadith/Importers/HadithImportPersister.php:920-926`).

4. **Constrain grading without losing scholarly nuance.** Use a lowercase canonical `grade_key` constrained to the small product taxonomy (initial default: `sahih`, `hasan`, `daif`, `mawdu`, `unknown`) and keep the unmodified `raw_grade`. Index `(grade_key, hadith_id)` for filters and `(hadith_id, scholar_id)` for attribution. The existing backed enum already defines the minimum taxonomy (`app/Domain/Hadith/Enums/HadithGrade.php:11-18`, `app/Domain/Hadith/Repositories/HadithRepository.php:151-179`).

5. **Repair chain invariants.** Add unique `(hadith_id, position_in_chain)`, unique `(hadith_id, narrator_id)`, and `CHECK(position_in_chain >= 1)`. Use `RESTRICT` on narrator deletion. If multiple independent chains per hadith are later sourced, then—and only then—add `hadith_isnads` plus `hadith_isnad_narrators` (`docs/hadith-schema.json:286-315`, `app/Domain/Hadith/Repositories/HadithRepository.php:617-631`).

6. **Make Quran references real FKs.** Use NOT NULL `quran_verse_id`, unique `(hadith_id, quran_verse_id)`, and `RESTRICT` on Quran verse deletion. Quran already guarantees unique `(surah_id, verse_number)`, so copied coordinate/name/text columns have no integrity value (`database/migrations/2025_11_29_100002_create_quran_verses_table.php:16-40`).

7. **Add only the missing forward relations that survive.** `Hadith` needs `sources()`, `keywords()`, and `relatedVerses()` so detail/export/review code can eager-load them. No relation should be added for tables being dropped (`docs/hadith-schema.json:239-247`).

8. **Use safe delete boundaries.** Parent aggregates and evidence identities should be `RESTRICT`; owned rows such as translations, source links, theme pivots, keyword links, commentaries, and Quran links may `CASCADE` with a deliberate hadith deletion. Scholar deletion should not erase historical grades; either restrict it or preserve a fallback attribution (`docs/hadith-schema.json:484-542`).

9. **Normalize identifiers, not content.** Apply lowercase validation to code/slug/locale/status/source/grade keys as planned. Keep names, Arabic/translated text, raw grades, commentary, relevance, and references byte-for-byte except documented whitespace/sanitization. The current grade parser mutates raw text into identifiers and thereby turns citations/punctuation errors into taxonomy rows (`app/Domain/Hadith/Importers/HadithImportPersister.php:641-654`).

10. **Start with the minimum proven indexes.** In addition to PK/FK indexes: collection `code`/`slug` unique; book and chapter composite uniques; hadith `text_hash`; translation unique `(hadith_id, locale)` + FULLTEXT `text`; isnad uniques above; grading `(grade_key, hadith_id)`; commentary `(hadith_id, locale)`; reverse theme pivot; keyword `(locale, keyword, hadith_id)`; source identity unique; Quran link unique; and public collection ordering `(active, featured, display_order)`. Drop every other index until an actual query justifies it.

## 6. Open questions

1. **Which importer is authoritative for the rebuild?** Recommended default: one collection-at-a-time Sunnah importer only; delete/retire the incompatible alternate sync services after it passes a MySQL smoke import. Current services disagree on table and column names (`app/Domain/Hadith/Services/HadithSyncService.php:264-274`, `app/Domain/Hadith/Importers/HadithImportPersister.php:313-368`).

2. **Where will narrator chains, themes, keywords, commentaries, and Quran relevance come from after Sunnah import?** Recommended default: name the enrichment source and acceptance counts before purging; otherwise keep only the schema required by a committed near-term writer. Sunnah transformer explicitly has no chain (`app/Services/Sunnah/SunnahDataTransformer.php:184-197`).

3. **Should metadata localization use JSON or translation rows?** Recommended default: JSON for small metadata and rows only for hadith/commentary text. This is the minimum-table choice and preserves five-locale flexibility, but it requires removing `HasLocalizedContent` from the three Hadith metadata models before import (`app/Domain/Shared/Traits/HasLocalizedContent.php:42-84`).

4. **What is the canonical grading taxonomy?** Recommended default: the existing five backed-enum keys, while always preserving the exact `raw_grade`; expand the enum only after a scholar-approved mapping. Structural/isnad classifications such as `mawquf`, `mursal`, and `munqati` may need a separate classification dimension rather than being forced into authenticity rank (`app/Domain/Hadith/Enums/HadithGrade.php:11-18`, `app/Domain/Hadith/Models/HadithGradingLevel.php:64-89`).

5. **Is chain position 1 nearest the Prophet or nearest the compiler?** Recommended default: honor the supplied/live-schema convention—nearest the Prophet—and change admin ordering/import accordingly. The model and repository currently assert the opposite (`docs/hadith-schema.json:286-301`, `app/Domain/Hadith/Models/HadithIsnad.php:11-19`, `app/Domain/Hadith/Repositories/HadithRepository.php:552-566`).

6. **Can one hadith have multiple independent isnad chains?** Recommended default: one chain per sourced hadith row; do not add a chain header table until incoming data demonstrates multiple chains. If it does, split chain identity from narrator links before import.

7. **Should Quran ranges remain a single editorial object?** Recommended default: expand each range to individual FK rows and share the same localized relevance. This trades a few rows for enforceable integrity (`docs/hadith-schema.json:663-686`).

8. **Are the 4,788 applications and 88 fiqh rulings human-authored and worth preserving?** Recommended default: export them before purge, but do not recreate their tables until a current product surface exists (`docs/hadith-schema.json:696-751`).

9. **Are optional-column population rates sufficient to justify significance, context, narrator school/region, review fields, and source verification metadata?** Unverified: the dump contains exact table row counts but no per-column NULL/distinct counts. Recommended default is to drop Sunnah-unpopulated hadith enrichment, retain factual narrator fields used by current filters, and retain review/provenance fields only where the rebuild has a writer and review workflow (`app/Domain/Hadith/Repositories/NarratorRepository.php:95-125`, `docs/hadith-schema.json:137-165`).

10. **Which live locale values are actually present?** The supplied verified measurement says only `ar`, `ar_notashkeel`, and `en`, while the dump note lists all five application locales without counts (`docs/hadith-schema.json:251-255`). This was not re-queried by design. Recommended default: treat the verified measurement as authoritative and correct the dump note before using it as an import acceptance baseline.

11. **Are `hadith_hadith_themes` and `hadith_fiqh_rulings` empty?** No according to the trusted dump: they contain 26,294 and 88 rows respectively (`docs/hadith-schema.json:587-597`, `docs/hadith-schema.json:721-739`). The contradictory wording in the brief should not drive a drop decision.

No live database, runtime query log, or network source was consulted. Consequently, actual NULL rates for most optional columns, external consumers outside this repository, and production query frequency are unverified; recommendations based on “unused” mean no read path was found in the inspected repository/models/services/controllers, not that an external consumer is impossible.
